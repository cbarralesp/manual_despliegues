Antes de empezar

En todo el proceso no necesitas Docker Hub: Render lee tu Dockerfile desde GitHub y construye la imagen en sus servidores. Tú solo subes el código con git push.

Render no tiene un entorno nativo para Java, por eso se usa el lenguaje Docker: el Dockerfile le explica cómo compilar y ejecutar la aplicación.

  • Un repositorio en GitHub con el backend (rama main), en tu cuenta personal.
  • Una cuenta en Render (render.com). Puedes entrar con GitHub.
  • Una cuenta en Supabase (supabase.com) para la base de datos PostgreSQL.
  • Una cuenta en Vercel (vercel.com) y un repositorio de GitHub con el frontend Angular, para la parte 3.
  • Un proyecto que compile en tu equipo (paso 3). Si falla ahí, también fallará en Render.

El orden del proceso y por qué

El proyecto tiene tres piezas que dependen unas de otras, y se despliegan en este orden: primero la base de datos, luego el backend y al final el frontend. El backend no puede funcionar sin base de datos: al arrancar se conecta a PostgreSQL y Flyway crea las tablas. Render, además, te pide los datos de conexión al crear el servicio. El front, a su vez, necesita la dirección pública del backend.

PartePasosDóndeQué se obtiene
1. Base de datos1SupabaseUn PostgreSQL vacío y sus datos de conexión (host, puerto, usuario, contraseña).
2. Backend2 a 6Eclipse, GitHub y RenderEl código preparado, subido y desplegado, conectado a esa base. Una URL pública de la API.
3. Frontend7 a 13GitHub y VercelEl tablero publicado, hablando con la API de Render.
Idea claveCada parte entrega un dato a la siguiente: de la base salen los datos de conexión (variables de entorno del paso 5), y del backend sale la URL pública que usa el front (paso 13). Si cambias el orden, el servicio arrancaría con error o el front no tendría con qué hablar.

Este es el primer paso: el backend necesita una base PostgreSQL, y los datos de conexión que obtengas aquí los usarás después en Render (paso 5). No hay que "subir" nada: el proyecto se crea vacío y Flyway crea las tablas la primera vez que arranca la aplicación.

No sigas al paso siguiente ni recargues una y otra vez: espera a que el estado deje de decir Coming up… y el botón Connect se vea activo (verde intenso). Si pasados los 5 minutos algún servicio sigue sin estar sano, revisa la documentación del enlace que muestra el propio panel.

1.6 Obtener los datos de conexión

Cuando el estado diga Healthy y el botón Connect esté en verde intenso, púlsalo.

Se abre Connect to your project. Entra en la pestaña Direct · Connection string (la tercera). La pestaña Framework, que es la que abre por defecto, no sirve para Spring Boot y muestra un aviso sobre la Data API: ignóralo, no pulses «Enable Data API».

En Connection Method está marcado Direct connection por defecto. Cámbialo a Session pooler.

Parte 2

Backend

Spring Boot · Docker · GitHub · Render. Se prepara el código, se sube a GitHub y se despliega conectado a la base.

2

Preparar el código

Se crean dos archivos en la raíz del proyecto (junto a pom.xml) y se modifican dos existentes.

kanban-backend\
├── pom.xml             ← se modifica
├── Dockerfile          ← se crea
├── .dockerignore       ← se crea
└── src\main\resources\application.yml   ← se modifica

2.1 Crear el Dockerfile

En Eclipse: clic derecho sobre el proyecto → New → File. El nombre es exactamente Dockerfile, sin extensión.

# ---------- Etapa 1: compilar con Maven ----------
FROM maven:3.9.9-eclipse-temurin-21 AS build
WORKDIR /workspace
COPY pom.xml ./
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B -DskipTests package

# ---------- Etapa 2: imagen liviana solo con el JRE ----------
FROM eclipse-temurin:21-jre-jammy
WORKDIR /app
RUN groupadd --system app && useradd --system --gid app app \
    && mkdir /app/logs && chown app:app /app/logs
COPY --from=build --chown=app:app /workspace/target/kanban-backend-*.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
PartePara qué sirve
Etapa 1 (maven)Compila el proyecto y genera el .jar.
Etapa 2 (jre)Imagen final pequeña: solo lo necesario para ejecutar.
useradd appLa aplicación no corre como administrador.
mkdir /app/logsEl proyecto escribe logs en logs/; sin la carpeta, el usuario app no podría crearla.
kanban-backend-*.jarDebe coincidir con el artifactId y la version de tu pom.xml.

2.2 Crear el .dockerignore

Evita enviar archivos innecesarios a la construcción. Mismo lugar, archivo .dockerignore:

target
.git
.idea
.vscode
.settings
logs
*.log

2.3 Agregar Actuator al pom.xml

Dentro de <dependencies> agrega esta dependencia. Da la ruta /actuator/health, que Render usa para saber si la aplicación está viva.

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
EclipseDespués de editar el pom.xml, clic derecho en el proyecto → Maven → Update Project… → OK, para que descargue la dependencia.

2.4 Modificar application.yml

Tres cambios en src/main/resources/application.yml.

a) Puerto. Render entrega el puerto en la variable PORT:

server:
  port: ${PORT:${SERVER_PORT:8083}}

b) Conexión segura a la base de datos. Supabase exige SSL. Agrega ?sslmode= al final de la URL:

spring:
  datasource:
    url: jdbc:postgresql://${DB_HOST:localhost}:${DB_PORT:5432}/${DB_NAME:kanban_db}?sslmode=${DB_SSL_MODE:prefer}

c) Exponer el health check y bajar el ruido del log SQL:

management:
  endpoints:
    web:
      exposure:
        include: health

logging:
  level:
    org.hibernate.SQL: ${LOG_LEVEL_SQL:INFO}

En tu equipo, la variable LOG_LEVEL_SQL=DEBUG vuelve a mostrar el SQL.

4

Subir el código a GitHub

Render lee el código desde GitHub, así que primero hay que subir los cambios. Los comandos se escriben en Git Bash.

4.1 Abrir Git Bash en la carpeta del proyecto

En el Explorador de archivos entra a la carpeta del backend (la que contiene pom.xml, ahora con Dockerfile y .dockerignore). Clic derecho en un espacio vacío → Mostrar más opciones → Open Git Bash here. El prompt debe terminar en el nombre de la carpeta y la rama (main).

4.2 Ver qué cambió

git status

Deben aparecer exactamente cuatro archivos: pom.xml y application.yml como modified, y .dockerignore y Dockerfile como untracked. Si aparece algo más, no lo agregues.

4.3 Agregar los archivos y crear el commit

git add Dockerfile .dockerignore pom.xml src/main/resources/application.yml
git commit -m "Preparar despliegue en Render"

Se agregan solo esos cuatro archivos, en vez de git add ., para no subir nada por accidente. Los avisos LF will be replaced by CRLF son normales en Windows y no afectan el resultado. El commit debe decir 4 files changed.

4.4 Subir a GitHub

git push origin main

Si es la primera vez en el equipo, Git abre el navegador para iniciar sesión en GitHub. Al terminar, la última línea muestra main -> main.

4.5 Comprobar en GitHub

Abre el repositorio en github.com y confirma que Dockerfile y .dockerignore aparecen en la raíz, junto a pom.xml.

Dato útilLos .gitignore ya excluyen target/ y logs/. Es correcto: el jar no se sube, Render lo compila.
Si algo fallaAuthor identity unknown: configura git config --global user.name "Tu Nombre" y git config --global user.email "tu@correo.com", y repite el commit. rejected … fetch first: el repositorio tiene cambios que no tienes; no fuerces el push y revisa antes.

6

Seguir el despliegue y comprobar el resultado

Render abre la pantalla del deploy. El estado pasa por Building y luego In progress. El título es el mensaje de tu último commit y Source es su código (aquí 84834b1, el que subiste a GitHub).

6.1 Build: Render construye la imagen

En Logs ves lo mismo que ejecuta tu Dockerfile: descarga las imágenes base, copia el proyecto, compila con Maven y arma la imagen.

Cuando aparece BUILD SUCCESS y COPY --from=build … kanban-backend-*.jar app.jar, el jar quedó dentro de la imagen. Después Render la sube a su registro (pushing layers).

6.2 Deploying: arranca la aplicación

Aparece ==> Deploying…. Ahora Render ejecuta el contenedor y espera a que responda. En el plan Free esto puede tardar entre 1 y 3 minutos.

Sé pacienteNo pulses Cancel. Espera a que el estado cambie a Live. Mientras tanto, en los logs deben aparecer las migraciones de Flyway y la línea Started KanbanApplication.

Cuando termina, el estado pasa a Deploy succeeded | Live (en verde) y la duración total queda registrada (aquí, unos 4 minutos). En los logs aparece Your service is live y la URL pública del servicio.

6.3 Comprobar que funciona

Cuando el estado sea Live, la URL pública del servicio aparece en los logs (Available at your primary URL) y bajo el nombre del servicio. Ten en cuenta que Render puede añadir un sufijo al nombre y cambiar el guion bajo por un guion, por ejemplo https://kanban-backend-hbmc.onrender.com.

El servicio se despierta

Si el servicio llevaba un rato sin recibir visitas, la primera petición muestra una pantalla de espera, «Service waking up…», y tarda entre 30 segundos y un minuto. Es el comportamiento normal del plan Free. Cuando termina, la página carga sola.

La ruta raíz devuelve un error 500

Si abres solo la dirección, sin ninguna ruta, verás un JSON con "status":500 y el mensaje «Ocurrió un error inesperado». Es lo esperado: la API no tiene nada en /. Que responda en el formato de la aplicación demuestra que el backend está funcionando.

Probar la API

Añade la ruta de la API a la dirección del servicio:

https://<tu-servicio>.onrender.com/api/tareas

Debe responder con la lista de tareas. No sale vacía porque la migración V2__datos_iniciales.sql inserta tres tareas de ejemplo. Verlas es la prueba de que se cumplió toda la cadena: Render ejecutó tu código, Flyway creó las tablas en Supabase y la API leyó los datos desde allí.

Ver los datos en Supabase

La prueba más clara de que backend y base están conectados es ver el resultado dentro de Supabase. En el panel del proyecto abre Table Editor (segundo ícono de la barra lateral). En el esquema public aparecen dos tablas que creó Flyway al arrancar el backend:

  • tarea: la tabla de tu aplicación.
  • flyway_schema_history: el registro de migraciones aplicadas. Muestra V1__crear_tabla_tarea.sql y V2__datos_iniciales.sql.

Para consultar los datos con SQL, abre el SQL Editor (tercer ícono), escribe la consulta y pulsa Run:

select * from tarea;

El resultado muestra las tres tareas de ejemplo, las mismas que devolvió la API y que ahora ve el tablero.

Dato útilEn la página principal del proyecto, la tarjeta Primary Database muestra cuántas conexiones hay abiertas (por ejemplo 6/60 conns). Esas conexiones las abre el backend de Render. En el mismo panel, Last migration dice «No migrations» porque se refiere a las migraciones propias de Supabase, no a las de Flyway.

Health check

Pendiente de captura. /actuator/health debe responder {"status":"UP"}.

Si falla

  • password authentication failed: DB_PASSWORD no es la contraseña real de Supabase.
  • Connection refused o timeout: revisa DB_HOST y que el puerto sea 5432.
  • El proceso se cae sin error claro: probablemente falta memoria; agrega JAVA_TOOL_OPTIONS (ver 5.5).

13

Conectar el front (Vercel) con el backend

Este paso supone que el front Angular ya está desplegado en Vercel (pasos 7 a 12). Falta que hable con el backend de Render.

13.1 Por qué el front muestra un error

El front llama a una ruta relativa, /api/tareas. En tu equipo, el archivo proxy.conf.json la reenvía a http://localhost:8083. En Vercel ese proxy no existe, así que el sitio abre pero no carga datos: aparece el banner rojo «Ocurrió un error inesperado» y las columnas vacías.

13.2 Crear vercel.json

En la raíz del proyecto del front (junto a package.json) crea el archivo vercel.json. Hace en Vercel lo mismo que el proxy local: reenvía las llamadas a /api al backend de Render.

{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://<tu-servicio>.onrender.com/api/:path*"
    },
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
  • Primera regla: todo lo que empiece con /api va al backend. Cambia <tu-servicio> por la dirección real de tu servicio en Render (aquí kanban-backend-hbmc).
  • Segunda regla: cualquier otra ruta de Angular sirve index.html, y evita el 404 al recargar la página.
  • No hay que cambiar código Angular. Tampoco hace falta tocar CORS: para el navegador la llamada va al mismo dominio, y es Vercel quien consulta a Render.

13.3 Subir el cambio a GitHub

Abre Git Bash en la carpeta del front. git status debe mostrar solo vercel.json como archivo nuevo.

git add vercel.json
git commit -m "Conectar el front con el backend en Render"
git push origin main

13.4 Vercel redespliega solo

No hay que hacer un deploy manual. Como el proyecto está conectado a GitHub, cada git push a main genera un despliegue nuevo en Vercel, en unos 20 a 30 segundos. Lo verás en la pestaña Deployments con el mensaje de tu commit, primero en Building y al terminar en Ready.

13.5 Comprobar

  1. Abre la URL de tu proyecto en Vercel (por ejemplo https://kanban-frontend-topaz.vercel.app). Debe mostrar el tablero con las tareas, sin el banner rojo.
  2. Prueba también /api/tareas en esa misma dirección: debe devolver el JSON del backend.

Estas tareas no vienen del front: pasan por toda la cadena Vercel → Render → Supabase. Para comprobar que también se guardan, crea una tarea con + Nueva tarea, recarga la página y verifica que sigue ahí. Después puedes verla en el Table Editor de Supabase.

Si tarda o fallaSi el backend de Render estaba dormido, la primera carga puede tardar hasta un minuto o mostrar un error. Espera y recarga. Es el comportamiento normal del plan Free.

13.6 Si cambias o recreas el servicio de Render

La dirección https://<servicio>.onrender.com pertenece a ese servicio. Si lo borras y creas otro, Render asigna una dirección nueva (el nombre más un sufijo) y la anterior deja de existir. Tu vercel.json sigue apuntando a la vieja.

Síntoma: el sitio abre, pero el tablero muestra el banner rojo y la consola del navegador (F12 → Console) dice Failed to load resource: … api/tareas … 404.

Cómo arreglarlo:

  1. En Render abre tu servicio nuevo, comprueba que diga Live y copia su dirección: está justo debajo del nombre.
  2. Prueba la API directo en el navegador, antes de tocar nada: https://<servicio-nuevo>.onrender.com/api/tareas. Debe mostrar el JSON de las tareas.
  3. En vercel.json cambia solo la línea destination, sin quitar /api/:path* del final.
  4. Guarda, haz commit y push. Vercel redespliega solo; espera a que quede en Ready y recarga con Ctrl + F5.
git add vercel.json
git commit -m "Apuntar el front al nuevo backend en Render"
git push origin main
Para que no vuelva a pasarNo borres el servicio de Render para actualizarlo. Usa Manual Deploy → Deploy latest commit. Si cambias de base de datos, edita las variables en Environment del mismo servicio: Render lo reinicia con la misma dirección.

13.7 Qué dirección de Vercel compartir

En el detalle de un despliegue, Vercel muestra dos direcciones en Domains:

  • nombre.vercel.app (icono de globo): el dominio de producción. Es fijo y se mantiene igual en cada despliegue. Es el que se comparte.
  • nombre-<código>-<usuario>.vercel.app: la dirección de ese despliegue puntual. Cambia con cada push y puede pedir iniciar sesión en Vercel.

Después del deploy

  • Despliegue automático. Cada git push a main genera un nuevo despliegue de producción. Eso es tu integración y entrega continua (CI/CD), sin configurar nada más.
  • Previews. Cada rama y cada pull request recibe su propia URL de prueba.
  • Historial. En Deployments puedes volver a una versión anterior si algo sale mal.
  • Dominio propio. En Settings → Domains puedes agregar el tuyo. Si no, queda nombre.vercel.app.

Anexo: conectarse a la base con HeidiSQL

Además del Table Editor de Supabase, puedes abrir la base desde tu equipo con un cliente como HeidiSQL (o DBeaver). Se conecta directamente a PostgreSQL con los datos del Session pooler del paso 1.6.

No hay una IP fijaPara conectarte usas el nombre del host (aws-1-us-east-1.pooler.supabase.com), no una dirección IP. Las IP detrás de ese nombre pueden cambiar, y por eso Supabase entrega un nombre. Tampoco hace falta autorizar tu IP: por defecto la base acepta conexiones con usuario y contraseña.

1. Crear la sesión

En HeidiSQL abre el Administrador de sesiones y pulsa Nueva. Completa la pestaña Ajustes:

Campo en HeidiSQLValor
Tipo de redPostgreSQL (TCP/IP)
Nombre de host / IPaws-1-us-east-1.pooler.supabase.com
Usuariopostgres.<ref-del-proyecto>
ContraseñaLa de tu proyecto en Supabase
Puerto5432
Base de datospostgres (escríbela: el campo trae solo un texto de ayuda)
Usa el Session poolerNo uses el host directo db.<ref>.supabase.co: solo funciona por IPv6 y desde muchas redes no conecta. Tampoco uses el puerto 6543 (Transaction pooler).

2. Activar SSL y guardar

  1. Abre la pestaña SSL y marca Usar SSL. Supabase exige conexión segura. No hace falta cargar certificados.
  2. Pulsa Guardar. Mientras la sesión tenga un asterisco (*), hay cambios sin guardar y el botón Abrir puede aparecer desactivado.
  3. Pulsa Abrir.

3. Ver las bases y las tablas

Al conectar, el panel izquierdo muestra los esquemas de la base. Los de Supabase (auth, storage, realtime…) son internos de la plataforma. Tu aplicación vive en el esquema public: ahí están la tabla tarea y flyway_schema_history.

4. Ejecutar consultas

Abre una pestaña de consulta (Ctrl + T), escribe una consulta y ejecútala con F9. Si hay varias consultas en la pestaña, selecciona la que quieres ejecutar antes de pulsar F9.

Ver todas las tareas:

select * from tarea;

Ver algunas columnas, ordenadas:

select id, titulo, estado, prioridad, fecha_limite
from tarea
order by id;

Contar tareas por estado:

select estado, count(*) as total
from tarea
group by estado;

Ver las migraciones que aplicó Flyway:

select installed_rank, version, description, script, success
from flyway_schema_history
order by installed_rank;

Las columnas de tarea son id, titulo, descripcion, estado, prioridad, fecha_limite, creada_en y actualizada_en.

Prueba para el aulaCrea una tarea desde el tablero de Vercel y vuelve a ejecutar select * from tarea;. Debe aparecer una fila más: el tablero escribe en la misma base que estás consultando.

5. Insertar, modificar y borrar tareas

También puedes escribir datos desde HeidiSQL. La tabla se llama tarea, en singular. No incluyas id, creada_en ni actualizada_en: la base los llena sola.

Insertar una tarea:

insert into tarea (titulo, descripcion, estado, prioridad, fecha_limite)
values ('Probar el despliegue', 'Revisar el tablero en Vercel', 'POR_HACER', 'ALTA', current_date + 3);

Insertar varias a la vez:

insert into tarea (titulo, descripcion, estado, prioridad, fecha_limite) values
  ('Crear el manual de Render', 'Con capturas del panel', 'POR_HACER', 'MEDIA', null),
  ('Conectar con HeidiSQL', 'Probar la conexión a Supabase', 'EN_CURSO', 'ALTA', current_date + 2),
  ('Subir el manual a GitHub', null, 'HECHA', 'BAJA', null);

Mover una tarea de columna o borrarla (cambia el 4 por el id de tu tarea):

update tarea set estado = 'EN_CURSO', actualizada_en = current_timestamp where id = 4;
delete from tarea where id = 4;
ColumnaValores permitidos
estadoPOR_HACER, EN_CURSO o HECHA
prioridadBAJA, MEDIA o ALTA
tituloObligatorio, máximo 100 caracteres
descripcionOpcional, máximo 500 caracteres
El límite de 3 en cursoEl tablero dice «máximo 3 en curso a la vez», pero esa regla la aplica el backend, no la base. Un insert directo con EN_CURSO se la salta y podrías dejar más de 3. Si insertas varias tareas, déjalas en POR_HACER.

Después de insertar, recarga el tablero con Ctrl + F5: las tareas aparecen en sus columnas.

¿Entrar al servidor de Render por SSH (MobaXterm)?

No es posible con el plan gratuito. Render lo avisa en la pantalla de creación: las instancias Free no soportan acceso SSH. Además, tu servicio es un contenedor Docker, no un servidor con una IP propia para entrar. Para ver qué hace la aplicación tienes estas opciones gratuitas:

  • Logs del servicio en el panel de Render (en vivo con Live tail).
  • Prueba local con Docker del mismo Dockerfile, donde sí puedes abrir una terminal dentro del contenedor.

El acceso por SSH y la pestaña Shell de Render requieren un plan de pago (en el menú lateral aparecen marcados con un rayo).

Anexo: publicar el manual en GitHub Pages

GitHub Pages publica sitios estáticos (HTML, CSS, JavaScript e imágenes) directamente desde un repositorio, gratis y sin servidor. Sirve para documentación, portafolios y manuales como este. No ejecuta backends. Una aplicación Angular necesita compilarse antes, y para eso Vercel es más cómodo.

Antes de empezar

  • Un repositorio en GitHub. En el plan gratis debe ser público.
  • Un archivo llamado index.html en la raíz del repositorio. Es la página de inicio del sitio.
  • Los archivos ya subidos a la rama main.

Paso 1. Subir los archivos

Desde la carpeta de tu proyecto:

git add .
git commit -m "Publicar sitio"
git push origin main

Paso 2. Abrir Settings → Pages

En el repositorio pulsa Settings y, en el menú de la izquierda, entra a Pages.

Paso 3. Elegir de dónde se publica

  1. En Source elige Deploy from a branch.
  2. En Branch selecciona main y la carpeta / (root).
  3. Pulsa Save.

Paso 4. Confirmar que se guardó

Aparece una franja azul con GitHub Pages source saved. Debajo, el texto cambia a Your GitHub Pages site is currently being built from the main branch. Eso significa que GitHub empezó a construir el sitio.

Paso 5. Esperar y abrir el sitio

La publicación tarda de uno a dos minutos. Para seguirla tienes dos opciones:

  • Recarga Settings → Pages. Cuando termina, arriba aparece la dirección de tu sitio con un botón para visitarlo.
  • Abre la pestaña Actions. Ahí corre un proceso llamado pages build and deployment. Cuando queda en verde, el sitio está publicado.

Cuando termina, arriba aparece el aviso Your site is live at con la dirección del sitio. Pulsa Visit site para abrirlo. El botón rojo Unpublish site retira el sitio: no lo pulses si quieres que siga publicado.

Al abrir la dirección ves tu index.html funcionando en Internet.

La dirección sigue siempre este formato:

https://<usuario>.github.io/<repositorio>/

Por ejemplo, para el usuario cbarralesp y el repositorio manual_despliegues: https://cbarralesp.github.io/manual_despliegues/.

Actualizar el sitio

No hay que repetir la configuración. Cada git push a main vuelve a publicar el sitio en uno o dos minutos.

Problemas comunes

Sale 404 al abrir la dirección

Espera un par de minutos y recarga. Si sigue igual, confirma que index.html esté en la raíz del repo, no dentro de una carpeta, y que en Pages esté seleccionada la carpeta / (root).

La página abre, pero sin estilos o sin imágenes

Casi siempre son rutas mal escritas. Usa rutas relativas como img/foto.png, sin / al inicio. GitHub Pages distingue mayúsculas y minúsculas: Foto.png y foto.png son archivos distintos.

No me aparece la opción de Pages o no me deja activarla

Revisa que el repositorio sea público. En el plan gratis, Pages no funciona con repositorios privados.

Hice push, pero el sitio no cambia

Espera uno o dos minutos y recarga con Ctrl + F5. Si sigue igual, revisa la pestaña Actions: un proceso en rojo indica un error de publicación.

Problemas comunes

El build falla: no encuentra kanban-backend-*.jar

El nombre del jar en el Dockerfile no coincide con el artifactId y la version del pom.xml. Ajusta la línea COPY --from=build.

El Dockerfile no se encuentra

Verifica que se llame exactamente Dockerfile (sin .txt), que esté en la raíz del repo y que en Render el Dockerfile Path sea ./Dockerfile.

Connection refused o timeout hacia la base

Usa el Session pooler de Supabase y DB_SSL_MODE=require. Revisa host, usuario y contraseña en las variables de entorno.

El front muestra un error de CORS

CORS_ORIGINS debe contener la URL exacta del front, sin / al final.

Al abrir la dirección del servicio sale un error 500

Es normal si abres solo la raíz (/): la API no tiene nada en esa ruta. Prueba /api/tareas o /actuator/health.

La primera petición tarda casi un minuto

Es normal en el plan Free: el servicio se duerme tras unos 15 minutos sin tráfico y tarda en despertar. Render lo avisa en el panel (Your free instance will spin down with inactivity, which can delay requests by 50 seconds or more). En una prueba real la primera respuesta tardó más de dos minutos. Espera y recarga: las siguientes peticiones son rápidas.

El tablero muestra error y la consola dice 404 en api/tareas

Casi siempre es porque recreaste el servicio de Render y su dirección cambió. Copia la dirección nueva y actualiza destination en vercel.json. Pasos completos en el apartado 13.6.

HeidiSQL: password authentication failed

Revisa que el usuario sea el del pooler, postgres.<ref-del-proyecto>, y no solo postgres. Revisa también la contraseña y que la sesión esté guardada (sin asterisco) antes de pulsar Abrir.

Front: El sitio abre en blanco o responde 404

Casi siempre es la carpeta de salida. En Vercel entra al proyecto → Settings → Build and Output Settings, activa el lápiz de Output Directory y escribe la ruta real:

dist/<nombre-del-proyecto>/browser

El nombre sale de la clave projects en tu angular.json. Guarda y vuelve a desplegar.

Front: El build falla

Abre Build Logs y lee las últimas líneas. Causas habituales:

  • El proyecto no compila en tu equipo con npm run build. Corrígelo primero ahí.
  • Un archivo escrito con otra mayúscula o minúscula en un import. Linux distingue entre Board.ts y board.ts; Windows no.
  • Falta una dependencia en package.json que solo tenías instalada de forma global.
Front: Mi repositorio no aparece en la lista

Repite el paso 9: Adjust GitHub App Permissions, agrega el repo y guarda. Si el repo es de una organización de GitHub, el plan Hobby no lo permite.

Límites de los planes gratis

Render (backend)

  • El servicio se duerme tras unos 15 minutos sin tráfico; despertar tarda entre 30 y 60 segundos.
  • El disco es efímero: no guardes datos en archivos locales. Los datos van en PostgreSQL.
  • Un git push redespliega solo si el servicio se creó con Git Provider. Con Public Git Repository hay que usar Manual Deploy → Deploy latest commit.
  • No hay acceso SSH ni pestaña Shell en el plan Free.
  • Para mantenerlo despierto en una demo, un monitor externo (por ejemplo UptimeRobot) puede consultar /actuator/health cada 10 minutos.

Supabase (base de datos)

  • El plan Free incluye 500 MB de base de datos, más que suficiente para este proyecto.
  • Un proyecto sin uso durante un tiempo puede pausarse.
